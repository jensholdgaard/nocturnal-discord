Code audit · August 2026 · For guild officers

## Nocturnal DKP Audit

A full review of the DKP bot's codebase, focused on the two problems everyone has felt on raid nights: it crashes constantly and it slows to a crawl when many auctions run at once. Every issue below comes with a concrete fix, and none of the fixes require changing the database schema — the bot can keep running against the existing production database.

- **88** findings (75 independently verified, 13 supplemental)
- **0** findings refuted on adversarial re-check
- **4** improvement tracks, phased by payoff
- **0** database schema changes required

## 1. Executive summary

The good news first: the bot's core accounting logic — how DKP is earned, how bids are ranked, how winners are chosen — is fundamentally sound, and it is the one part of the codebase covered by automated tests. The guild's DKP ledger is not built on a broken foundation.

The problems live in the layer that connects that logic to Discord and to the database, and they are systemic rather than isolated:

- **There is no safety net anywhere.** The bot has zero process-level error handling. In modern Node.js, a single unhandled failed operation — a Discord button click acknowledged a fraction of a second too late, a momentary network hiccup to the database — terminates the entire process. The code contains dozens of places where exactly that can happen, including background jobs that run every 10 seconds around the clock. This single architectural gap is what turns every small transient error into a full crash.
- **The database is queried in the most expensive way possible.** There is not a single index in the database, so every query scans entire collections. Hot paths download megabytes of data to read one number. The production database is MongoDB Atlas's free tier — shared, throttled, and network-distant — which multiplies every one of these costs. This is the root of the slowness, and the slowness in turn causes crashes (slow responses miss Discord's 3-second acknowledgment window).
- **Several race conditions and logic bugs can corrupt the DKP economy itself** — negative balances, double-charged or never-charged auction winners, double-awarded raid ticks, and a tie-breaker that can hand loot to the wrong player. These are invisible until someone disputes a loot decision, which is exactly when you least want them.

The headline: roughly 2–4 days of focused work (Phase 1) would eliminate the overwhelming majority of crashes, and about a week more (Phase 2) would take commands from multi-second waits to sub-second responses. Neither phase touches the database schema or changes any behavior officers rely on. The fairness fixes and code cleanup can then follow at a calmer pace.

## 2. How this audit was done

The entire codebase (~35 source files) was reviewed by five independent review passes, each with a different lens: crash stability, database usage, Discord API timing, concurrency/race conditions, and code simplification. Every finding was then adversarially re-verified by separate reviewers instructed to refute it against the actual code. 75 findings survived that process with zero refuted (a handful had their severity or mechanism corrected, and those corrections are reflected here). A final completeness pass surfaced 13 additional issues; the two most consequential of those (the never-debited long-auction winners and the tie-breaker bug) were subsequently confirmed line-by-line in the source.

Ground rule for every recommendation: the bot will connect to the existing production database, so the data schema must not change. Every fix below respects this — the only database-side changes proposed are indexes, which are additive, invisible to the application, and reversible.

Where this report cites code, it uses file:line references (e.g. commands/startbid.js:117) so any developer can jump straight to the spot.

## 3. Anatomy of yesterday's crash

The crash log from yesterday is worth walking through, because it is a perfect specimen: nearly every systemic problem in this report participates in it.

1. A short auction ends and the officer clicks "Confirm Winner/s". Discord gives the bot exactly **3 seconds** to acknowledge that button click.
2. **The bot is busy.** The raid tick has just fired 40 parallel database writes at the free-tier cluster, other auction embeds are being edited, and the event loop is congested. The acknowledgment — `i.update()` at commands/startbid.js:117, which is the first response to the click — goes out after the 3-second window has closed.
3. **Discord rejects it: DiscordAPIError[10062] Unknown interaction.** This is a routine, non-fatal error — every large bot sees it daily and simply ignores it.
4. **Nothing catches it.** The button handler has no try/catch, and the process has no global rejection handler. Node.js does what it does by default with an unhandled rejection: it terminates the process, exit code 1.
5. **The crash lands at the worst possible moment.** The winner had already been announced, but the crash happens before the DKP deduction loop (startbid.js:121–143). The winner keeps their points. Every other auction in progress existed only in memory — all of their bids are gone, and their "I want to bid" buttons are left dead on screen.
6. **Recovery is slow.** The Pterodactyl panel restarts the bot, which runs git pull + npm install on every boot — several minutes of downtime, mid-raid, plus a full re-registration of all slash commands.

The lesson: the crash was not caused by an exotic bug. It was a routine, expected Discord timing error meeting a codebase with no error handling, in-memory-only auction state, and a slow restart path. Fix the safety net and the same event becomes a single ignored log line.

## 4. Why the bot crashes

One multiplier, many triggers. The multiplier is the missing safety net; the triggers are all the places a routine error can escape unhandled. These are the confirmed crash paths, ranked by how often they are likely to fire on a real raid night.

- **Critical (hours) — The multiplier: zero process-level error handling.** index.js registers no `process.on('unhandledRejection')`, no `process.on('uncaughtException')`, and no Discord client error/shardError handlers. Any promise rejection that escapes a handler — and dozens can — terminates the bot. Fix: a ~10-line block in index.js that logs these events instead of dying. Single highest-leverage change in this report.
- **Critical (hours) — Background jobs run unprotected every 10 seconds, 24/7.** worker/Worker.js:12–17 runs database polling loops every 10 s / 60 s / 1 h with no error handling at all. Any transient hiccup from the free-tier Atlas cluster kills the bot even when nobody is using it. Fix: try/catch each loop body; add an "already running" guard.
- **Critical (a day) — One bad long auction = a crash loop every 60 seconds.** Worker.js:91–108 processes expired long auctions fire-and-forget; looking up each bidder throws if a player document is missing. Crash happens before the auction is marked finished → re-processed next cycle → crash loop every minute. Fix: process one at a time inside try/catch; skip missing bidders.
- **High (hours) — A player with closed DMs clicking "I want to bid" kills the bot.** utils/Logger.js:294–308: when the DM can't be delivered, the error path calls i.reply() on an already-acknowledged interaction — which throws inside a catch block. Fix: await the ack, followUp in the failure path, wrap the handler. (Longer term: replace the DM flow with a Discord modal — no DMs needed at all.)
- **High (hours) — Every auction start and end is an unprotected crash window.** Auctioner/Auctioner.js:30–50 close timer does DB lookups and invokes the winner callback unprotected. The bell sound (startbid.js:180–183) is likewise unprotected, on a voice library running on an unsupported Node version. Fix: try/catch the close callback; bell strictly best-effort.
- **High (1–2 days) — Auctions live only in memory — every crash erases them.** Auctioner.js:23. Fix: persist short auctions to the existing auctions collection at start; let the worker finalize orphans after restart (mechanism exists for long auctions).
- **Medium (hours) — A long tail of smaller crash paths.** Un-awaited DKP write loops; pagination buttons in /listplayersdkps, /dkphistory, /searchlogs; fire-and-forget debug logger; raid-end embeds exceeding the 4096-char limit; Cancel racing natural close; two reply paths in index.js escaping its own try/catch. Same medicine everywhere: await, wrap, treat 10062/10008/40060 as non-fatal.

## 5. Why the bot is slow

The slowness is in the code's database access patterns, amplified by the free-tier cluster (shared CPU, throttled I/O, 512 MB storage cap, real network latency per round-trip).

**The big four:**

- **Critical (hours) — Zero database indexes.** Every player lookup, raid check, auction scan reads the whole collection. The worker runs "is there an active raid?" ~8,640×/day/guild as a full scan. DKP list sorting happens in cluster memory. Fix: ~8 indexes, one-time script (see findings index #18).
- **Critical (hours) — Reading one player downloads the entire raid history.** getPlayer() (DKPManager.js:183–199) fetches every non-deprecated raid document — rosters included — to compute attendance on every call, even balance-only calls. Fix: skip attendance where unused; projections where used.
- **High (hours) — Player documents grow forever and are always fetched whole.** Unbounded log arrays; reading 40 bidders' balances at auction close can transfer 15–20 MB for 40 integers. Fix: projections + one batched query.
- **High (a day) — Chatty query patterns everywhere.** One /bid = 5 sequential round-trips; one raid tick = ~41 parallel writes (2 bulk ops would do); /parsedkps with 40 characters = 80 sequential round-trips; options re-read every 10 s; debug logger inserts with no expiry. Fix: consolidate (5→2, 41→2, 80→2), cache options, TTL index on debuglog.

**Secondary contributors:** item scraping with no timeout + heavyweight DOM parse on the main thread (fix: 5 s timeouts, in-memory item cache — EQ items never change, lighter parser); synchronous error logging blocking the event loop (index.js:85–90); Mongo client defaults unsuited to shared free tier (100-conn pool, infinite timeouts, no compression — ~5 options in db.js); commands never defer.

**The vicious circle:** no indexes → slow queries → missed 3-second windows → 10062 → no error handling → crash → restart (git pull + npm install + re-registration) → cold caches → more slowness.

## 6. DKP fairness & integrity

- **High (hours) — Long-auction winners are never charged — verified.** No code path debits winners of /startlongbid auctions. The only deductions in the codebase are the short-auction confirm button and manual /removedkp. Fix: add the missing debit in the worker's finalization — or if manual debiting is policy, post the exact list of debits owed.
- **High (hours) — The attendance tie-breaker can award loot to the wrong player — verified.** Auction.js:122–123 draws the random index over the correct short-list but applies it to the wrong array (sorted only by bid). Example: A bids 100 @50% attendance; B and C bid 100 @90% — A wins half the time. Two adjacent branches are dead code. Long-auction bids are stored without attendance at all, so their tie-breaks are already coin flips. Fix: two lines + a unit test.
- **High (hours) — Double-spending across parallel auctions → negative balances.** Balance checked at bid time, debited at confirm with no sufficiency condition. 100 DKP can win two 100-bids → −100. Fix: conditional debit + channel alert.
- **Medium (hours each) — Race conditions that corrupt the ledger.** >10 s tick can run twice (double DKP); double-submitted /bid → duplicate entries, one player wins two items; two simultaneous /startraid → two active raids, phantom ticks; concurrent first-time writes split a new player into two documents; slow finalization re-run with a new random tie-break → two contradictory winner announcements. Fixes: unique indexes (players; partial unique on active raid), atomic conditional updates, in-memory tick lock.
- **Medium (hours) — Smaller integrity leaks.** /removedkp accepts negative amounts (disguised credit logged as removal); a transient Discord hiccup in the 10 s poll permanently ends the active raid (Worker.js:26–35), silently; bids landing during the close window are counted or dropped nondeterministically; /parsedkps mispasses a flag and writes corrupted "null raid" entries; /registercharacter reports success when nothing saved; character matching case-sensitive vs capitalized EQ logs.

## 7. The four improvement tracks

- **Track 1 — Stability safety nets (2–4 days).** Global error handlers; try/catch around every button/collector handler and worker loop; defer first, work after; await every DB write before confirming; bell + debug logging non-fatal; timeouts on external HTTP; async error logging. → Crashes drop to "rare and newsworthy". Highest leverage per hour.
- **Track 2 — Database performance (3–5 days).** Index set (incl. TTL on debuglog); skip unneeded attendance; projections; tick 41→2 writes; consolidate /bid and /parsedkps; cache guild options; Mongo client options; defer slow commands. → Sub-second commands; fixes "slow with many auctions".
- **Track 3 — DKP integrity (~1 week).** Conditional debits; fix tie-breaker; debit long-auction winners; atomic bid writes and finalization; unique indexes (players, single active raid); tick serialization; input bounds; stop ending raids on transient errors; persist short auctions from start. → Trustworthy ledger under concurrency; auctions survive restarts.
- **Track 4 — Simplification & hygiene (1–2 weeks, incremental).** Merge ~80 % duplicated auction commands; one pagination helper; one bid-validation implementation; fix the 90-millisecond raid-deprecation default (stored unit is ms, default forgot the conversion); centralize defaults; remove dead code/deps and the ~75 MB voice stack; migrate 55 deprecated ephemeral options; unify the two permission models; make the test suite runnable and safe (currently hardcodes localhost and wipes the 'DKP' database); register slash commands only on change.

## 8. Suggested roadmap

## 9. Hosting environment notes

- **Node version mismatch.** Prod runs Node v20.20.2; project requires ≥22.12 (voice library EBADENGINE at every boot). Align image to Node 22+ or drop the voice stack.
- **Every boot reinstalls the world.** git pull + npm install --production on every start; minutes of downtime per crash; dozens of pointless global slash-command re-registrations per day (rate-limited endpoint). Install on deploy or adopt the prepared Docker deployment.
- **Atlas M0 free tier.** Shared, throttled, latency-distant, 512 MB cap being eaten by debuglog. Tracks 1–2 make the bot a polite M0 citizen; TTL index stops the bleed.
